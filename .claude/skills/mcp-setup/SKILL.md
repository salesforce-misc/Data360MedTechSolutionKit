## Purpose

Register and authenticate the four Salesforce hosted Standard MCP servers, all pinned to the org whose External Client App was just deployed:

1. **`salesforce-sobject-all`** — generic sObject CRUD + SOQL + schema + related records. Used by installer + verification skills via `mcp__salesforce-sobject-all__*` tools.
2. **`salesforce-data-cloud-queries`** — Data Cloud DMO / DLO queries via SQL. Used by Data Cloud skills via `mcp__salesforce-data-cloud-queries__*` tools.
3. **`salesforce-data360`** — Data360 Connect API operations (data streams, activations, calculated insights, DMO/DLO/mapping CRUD). Used by Data360 skills via `mcp__salesforce-data360__*` tools. **Replaces the legacy stdio `data360` JAR-based MCP** — the JAR has been retired.
4. **`salesforce-headless-360`** — Generic Salesforce API dispatcher (discover / describe / dispatch / dispatch_readonly). Routes calls under `/services/data/*` (public Connect + REST API surface). Used by skills like `/embed-service-agent-on-experience-site` (Step 5 — ESA publish) via `mcp__salesforce-headless-360__*` tools.

All four registrations reuse the SAME Consumer Key + Secret auto-generated by the External Client App `Salesforce_DC_Prod_Org` — the user pastes them once, and this skill wires up all four MCPs. Transport is HTTP for all four (Salesforce's hosted `api.salesforce.com/platform/mcp/v1/*` endpoints), auth is OAuth 2.0 authorization-code with PKCE + client secret.

**The user provides exactly two values manually:** the auto-generated Consumer Key and Consumer Secret from the deployed External Client App. Everything else — Org URL, environment-derived login URL, MCP registrations, org-side activation, OAuth authentication, verification — is automatic.

### Step 5 — Validate credentials via OAuth probe (fail fast)

**Goal:** catch a bad Key/Secret combination NOW, before touching the MCP registry. The `client_credentials` grant requires the External Client App's OAuth policy to allow it — this probe verifies both creds and policy in one shot.

**Why we probe `$ORG_URL` (My Domain) and NOT `$LOGIN_URL`:** Salesforce enforces `client_credentials` grants against the org's own My Domain endpoint (e.g. `https://myorg.my.salesforce.com/services/oauth2/token`). Hitting `https://login.salesforce.com/services/oauth2/token` returns `invalid_grant: "request not supported on this domain"` on every org that has My Domain enabled — which is every production org since Winter '22 and every sandbox since Spring '23.

```bash
HTTP_BODY=$(curl -sS -m 10 -X POST "$ORG_URL/services/oauth2/token" \
    -H "Content-Type: application/x-www-form-urlencoded" \
    -d "grant_type=client_credentials" \
    -d "client_id=$KEY" \
    -d "client_secret=$SECRET" 2>/dev/null)

ACCESS_TOKEN=$(echo "$HTTP_BODY" | python3 -c "import json,sys; d=json.loads(sys.stdin.read() or '{}'); print(d.get('access_token',''))" 2>/dev/null)

if [ -z "$ACCESS_TOKEN" ]; then
    ERR_CODE=$(echo "$HTTP_BODY" | python3 -c "import json,sys; d=json.loads(sys.stdin.read() or '{}'); print(d.get('error','unknown'))" 2>/dev/null)
    ERR_DESC=$(echo "$HTTP_BODY" | python3 -c "import json,sys; d=json.loads(sys.stdin.read() or '{}'); print(d.get('error_description','(no description)'))" 2>/dev/null)
    echo "❌ OAuth probe FAILED — Salesforce rejected the credentials"
    echo "   error:             $ERR_CODE"
    echo "   error_description: $ERR_DESC"
    echo ""
    echo "Common causes:"
    echo "  • Consumer Key or Consumer Secret copied incorrectly (whitespace, missing chars)"
    echo "  • Wrong environment selected — using Production URL against a sandbox org (or vice versa)"
    echo "  • The External Client App's OAuth policy does not allow the client_credentials flow"
    echo "  • The 'Run As' user configured on the ECA is missing, inactive, or has no relevant permset"
    echo ""
    echo "Re-run /mcp-setup with corrected values. Do NOT register the MCP with bad creds."
    exit 1
fi

echo "✅ OAuth probe succeeded — credentials valid (got access_token)"

# Don't keep the token in the environment — we only needed proof that the creds work
unset ACCESS_TOKEN HTTP_BODY
```

### Step 8 — Register + authenticate the four hosted MCP servers

Runs one script that does five things in sequence, all headless: registers all four servers in `~/.claude.json`, mints OAuth tokens for each via PKCE, writes credentials to `~/.claude/.credentials.json`, detaches per-server sentinels, clears the "Needs Auth" cache.

> **⛔ STOP — READ BEFORE EXECUTING THIS STEP**
>
> This step is **CLI-only** — one command: `bash scripts/authenticate-mcp-server.sh "$ORG" "$KEY" "$SECRET"`.
>
> Do NOT open a browser. Do NOT use Playwright. Do NOT trigger `claude mcp` interactive OAuth (that would open a browser popup — this step is designed to avoid that). Do NOT print "Please complete OAuth in your browser" text. The script mints access tokens via direct `/services/oauth2/authorize` + `/services/oauth2/token` POSTs using the Consumer Key/Secret from Step 2, then writes them into `~/.claude/.credentials.json`. If the script fails, DEBUG THE SCRIPT — do not fall back to a browser.

**Preconditions:**
- Step 5 succeeded (OAuth probe passed)
- Step 7 succeeded (all 4 hosted MCPs Active in the org)
- The `sf` CLI session for `<org_alias>` is authenticated

**Execution:**

```bash
bash scripts/authenticate-mcp-server.sh "$ORG" "$KEY" "$SECRET"
RC=$?

if [ "$RC" -ne 0 ]; then
    echo "❌ authenticate-mcp-server.sh FAILED for org '$ORG'."
    exit 1
fi

echo "✅ All 4 hosted MCP servers registered + authenticated"
```

**What the script does (all 4 hosted Standard MCP servers in one pass):**
1. Exchanges the `sf` CLI access token for a Salesforce browser session cookie via `frontdoor.jsp` + `contentDoor` (ONCE — shared across all 4 servers)
2. **Auto-registers all 4 hosted servers in `~/.claude.json`** (no manual `claude mcp add` needed) — `salesforce-sobject-all`, `salesforce-data-cloud-queries`, `salesforce-data360`, `salesforce-headless-360`
3. For EACH server: calls `/services/oauth2/authorize` with `prompt=none` + fresh PKCE, exchanges the auth code for access + refresh tokens at `/services/oauth2/token`
4. Writes the tokens into `~/.claude/.credentials.json` under `<server-name>|<hash>` (falls back to a URL-only hash; a per-server sentinel promotes tokens to Claude Code's actual hash key when the extension creates its stub after reload)
5. Clears the servers' entries from `~/.claude/mcp-needs-auth-cache.json` so the MCP panel doesn't remember stale "Needs Auth" verdicts

**Windows quoting requirement — every inline python3 block in this script MUST use `python3 <<'PY' ... PY` with variables passed via env, NEVER `python3 -c "..."` with `${...}` interpolation or escaped quotes.** On Windows/Git-Bash (MSYS/Cygwin bash), the shell mangles `\"`, `\\''`, and mixed single-double-quote escaping inside `python3 -c "..."` — the exact failure mode is `SyntaxError: closing parenthesis ']' does not match opening parenthesis '('` at whichever line contains a character-class regex with escaped quotes. Fix: use an env-var + quoted-heredoc (`<<'PY'`) so bash treats the python source as literal. Anyone re-editing the script must preserve this pattern or it silently fails to POST the approval and the auth code is never issued.

Script source: [scripts/authenticate-mcp-server.sh](../../../scripts/authenticate-mcp-server.sh).

**Credential-key hashing (why the script runs a sentinel):** Claude Code stores OAuth tokens in `~/.claude/.credentials.json` under a key of the form `<server-name>|<16-hex-hash>`. The hash folds in URL + client_id + callback port + more — the exact formula is not documented and cannot be reliably reconstructed from Python. If the script writes tokens under a hash Claude Code isn't watching, the token exists on disk but the MCP panel reports "Needs Auth" forever.

The script defends against this in three layers:

1. **Bootstrap:** runs `claude mcp list` first (if the CLI is on PATH). This forces Claude Code to attempt a connection against each registered server, which creates an empty stub entry under its own correctly-hashed key. If this succeeds, the script writes tokens directly to the correct key on first try — no further intervention needed.

2. **Sentinel (detached background process, one per server):** even if the bootstrap step didn't fire, the script writes tokens to a URL-only-hashed key AND detaches [scripts/all-mcp-server-sentinel.py](../../../scripts/all-mcp-server-sentinel.py) which polls `~/.claude/.credentials.json` every 2 seconds for up to 5 minutes. The moment Claude Code creates its own correctly-hashed empty stub (which it does on any MCP list, health-check, or window reload), the sentinel copies the tokens into it and prunes the legacy URL-only key. Fully hands-off. Logs to `~/.claude/<server-name>-sentinel.log` for debugging.

3. **VSCode reload:** the user reloads the VSCode window once after the script exits. This forces the extension to reload, which triggers stub creation, which triggers the sentinels to promote tokens. End-to-end wall-clock: ~5–10 seconds after reload.

**If it still shows "Needs Auth" after reload:** exceedingly rare with the sentinel in place. Check `~/.claude/<server-name>-sentinel.log` — if the sentinel timed out (5 min) without seeing a stub appear, Claude Code isn't creating stubs. Manually reload the VSCode window and re-run the auth script — the sentinel will detect the fresh stub on the next run.

Then clear both secrets from the environment:

```bash
unset KEY SECRET
```

**When `claude` CLI is on PATH** — use `claude mcp list`:

```bash

grep -q "^salesforce-sobject-all"        /tmp/mcp_list.txt || MISSING="$MISSING salesforce-sobject-all"

    echo "❌ MCP verification FAILED — missing:$MISSING"
    echo "   Full 'claude mcp list' output:"
    cat /tmp/mcp_list.txt
    rm -f /tmp/mcp_list.txt

echo "✅ MCP registry verified — all 4 hosted MCPs present"

```

## Error Handling

### OAuth probe (Step 5) returns `invalid_client`

Almost always means the Consumer Key was copied with leading/trailing whitespace or missing characters. Re-run `/mcp-setup` and paste again carefully (use Ctrl+A / Cmd+A to select the full value in Setup before copying).

### OAuth probe returns `invalid_grant` with description `"request not supported on this domain"`

You're probing the wrong endpoint — likely `login.salesforce.com` or `test.salesforce.com`. For orgs with My Domain enabled (every modern Salesforce org), `client_credentials` grants must hit the org's OWN My Domain URL, e.g. `https://<yoursubdomain>.my.salesforce.com/services/oauth2/token`. Step 5 probes `$ORG_URL` (auto-discovered from `sf org display`) — do not change it back to `$LOGIN_URL`.

### OAuth probe returns `invalid_grant` with any other description

The Consumer Secret is wrong, OR the External Client App's OAuth policy doesn't allow the `client_credentials` flow, OR the Run-As user (component 5 of `/external-client-app-deploy`) is inactive/deactivated. Check Setup → External Client App Manager → Salesforce_DC_Prod_Org → Policies tab → OAuth Policies → Permitted Users / Flow Enablement, and confirm the user in `<clientCredentialsFlowUser>` is Active. To re-verify the Secret itself, re-open Setup → External Client App Manager → Salesforce_DC_Prod_Org → Settings tab → OAuth Settings → click "Consumer Key and Secret" → enter the email-verification code → copy both values again.

### OAuth probe returns network error / timeout

Rare with `$ORG_URL` since it's the org's own host. Usually means DNS resolution failure or a corporate proxy blocking outbound HTTPS. Confirm you can `curl -sS $ORG_URL/services/data/` in the same shell — if that fails, fix the network path first.

### `activate-mcp-servers.sh` fails on `data.data360` or `data.data-cloud-queries`

- Verify Data Cloud is enabled in the org (should be — `/feature-enablement` handles this).
- Verify the ECA has the `mcp_api` and `refresh_token` OAuth scopes (`ps-eca/` metadata does this by default).
- The script retries per-server; if only one server fails, the error message names which. Fix that server's specific issue and re-run — the script is idempotent.

### `authenticate-mcp-server.sh` fails at PKCE step

Usually means the Salesforce session cookie is stale. Run `sf org login web --alias $ORG` to refresh, then re-run the auth script.

### MCP panel still shows "Needs Auth" after reload

Check `~/.claude/<server-name>-sentinel.log` for that specific server. If the sentinel timed out, Claude Code never created its stub — reload VSCode again and re-run the auth script; the sentinel will detect the fresh stub on the next run. If credentials on disk look right but the panel still fails, check that `~/.claude/mcp-needs-auth-cache.json` doesn't have a stale entry (delete the entry for that server and refresh the panel).

### `OAUTH_AUTHORIZATION_BLOCKED: Cross-org OAuth flows are not supported for this external client app`

The ECA is deployed to org A, but you're authenticating for org B — the two must match. Fix: run `sf org display --target-org $ORG` and confirm the instance URL matches the org where the ECA was deployed.
